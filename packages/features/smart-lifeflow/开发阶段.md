开发 Smart LifeFlow 这样一个集成了**离线优先、双向同步、复杂业务逻辑（如排程算法、复发规则）**的系统，最忌讳的是“大爆炸式开发”（即把所有功能写完再联调）。

我们需要采取 **“洋葱剥皮”** 或 **“垂直切片”** 的策略：从最核心的数据层向外扩展，先跑通链路，再丰富功能。

以下是建议的 **6 个里程碑 (Milestones)** 开发路径：

---

### 阶段一：基础设施与同步骨架 (Infrastructure & Sync Skeleton)

**目标**：跑通“数据库 -> DAO -> SyncService -> 后端 -> 数据库”的闭环。不涉及具体 UI，只看 Log 和数据库。

1. **服务端 (Backend)**
    * 搭建 Spring Boot + PostgreSQL 基础框架。
    * 实现 `TimeProvider` 接口 (`GET /time`)。
    * 实现 **Unified Batch Sync** 接口 (`POST /sync`) 的空壳（接收 JSON，解析 DTO，暂不存库，只打印日志）。
    * 配置 Redis 环境（用于去重和幂等）。

2. **客户端 (Client - Data Layer)**
    * 完善 `AppDatabase` 类，实现 `onCreate` 中的索引创建。
    * 实现 `TimeProvider` (单调时钟 + 启动 ID 检测)。
    * **实现 Sync Engine 核心**：
        * `SyncMeta` 表的读写。
        * `SyncService` 的请求构建、重试机制、Ack 处理逻辑。
        * *暂不需要实现具体的业务表同步，先跑通协议握手。*

3. **验证点**
    * 客户端发起同步，服务端能收到请求头里的 `X-Client-Time` 并进行偏差校验。
    * 服务端返回 Mock 数据，客户端能正确解析。

---

### 阶段二：核心 CRUD 与 垂直拆分验证 (Core Data & Split Verification)

**目标**：实现核心业务数据的增删改查，并验证 `TaskDefinition` 和 `TaskState` 的拆分逻辑是否跑得通。

1. **客户端 DAO 层**
    * 实现 `ActivityDao`, `PlanDao`。
    * **重点**：实现 `TaskRepository`。
        * 写入时：事务内同时插入 `TaskDefs` 和 `TaskStates`。
        * 读取时：实现 `JOIN` 查询，将两张表聚合为 `Task` 领域对象。
    * 实现 `json_converter` 的具体逻辑（复发规则序列化）。

2. **服务端同步逻辑**
    * 实现 `Task` 和 `Activity` 的 LWW 处理逻辑（Time Clamping, Ack, Echo）。
    * 实现 `Plan` 的级联删除逻辑（标记 `deleted_at`）。

3. **UI (原型级)**
    * 一个极其简陋的列表页：显示任务。
    * 一个添加按钮：添加测试任务。
    * *目的：产生真实数据来测试同步。*

4. **验证点**
    * **冲突测试**：手机改标题，平板打卡。同步后，手机看到进度变了，平板看到标题变了。验证垂直拆分有效。

---

### 阶段三：规划引擎 (The Planning Engine)

**目标**：实现“晨间规划”的核心算法。这是纯逻辑层，不涉及太多同步（除了结果存库）。

1. **复发规则引擎 (Recurrence Engine)**
    * 编写纯 Dart 单元测试。
    * 输入：`TaskRecurrence` (JSON), `LastDoneTime`, `TargetDate`。
    * 输出：`bool isDueToday` (今天是否该做)。
    * *难点：处理 Flexible 和 Relative 模式的计算。*

2. **候选池逻辑**
    * 实现 `CandidateService`：查询所有 Active 任务，通过规则引擎筛选出今天的 Candidates。

3. **角斗场算法 (The Arena)**
    * 实现两两对比排序算法（如归并排序变种）。
    * 输入：List of Tasks。
    * 输出：带有 `sortOrder` (Double) 的 `ScheduleItems`。

4. **UI 实现**
    * 实现“晨间规划”流程页面：候选选择 -> 对比排序 -> 确认生成。

5. **验证点**
    * 规划完成后，数据库 `ScheduleItems` 表中生成了正确的数据。
    * 同步后，其他设备能看到同样的“今日计划”。

---

### 阶段四：执行与流水记录 (Execution & Logging)

**目标**：实现打卡、计时和数据聚合。

1. **客户端 DAO 升级**
    * 实现 `ActivityLogDao`。
    * 实现 **Smart Merge** 相关的查询（按逻辑日聚合 Log 计算 `currentValue`）。

2. **状态流转逻辑**
    * **打卡动作**：
        1. Insert `ActivityLog`。
        2. Update `TaskState.currentValue` (快照)。
        3. Check `currentValue >= target`? Update `TaskState.status` & `ScheduleItem.status`。
    * **专注模式 (Focus)**：实现一个前端计时器，结束时生成 Log。

3. **服务端 Delta 同步 (如果需要)**
    * 如果 Log 表采用 Insert-Only 策略，服务端只需处理去重。
    * 如果 Log 允许修改备注，实现 Log 的 LWW。

4. **UI 实现**
    * 首页“今日视图”：渲染 `ScheduleItems`。
    * 打卡交互：长按/点击打卡，进度条动画。

5. **验证点**
    * **逻辑日测试**：在凌晨 2 点打卡，确认 `logicalDate` 归属正确，且统计归入“昨天”。

---

### 阶段五：可视化与反馈 (Visualization & Review)

**目标**：展示统计报表和双轨时间轴。此阶段主要涉及复杂的 Read 查询。

1. **查询服务**
    * 实现 `StatsRepository`。
    * 编写 SQL 聚合查询：按 `activityId` 分组统计时长；按 `logicalDate` 统计趋势。

2. **双轨时间轴 UI**
    * 左侧渲染 `ScheduleItems` (Plan)。
    * 右侧渲染 `ActivityLogs` (Reality)。
    * 实现“磁吸修正”交互（拖拽 Plan 生成 Log）。

3. **通知模块**
    * 实现 `NotificationScheduler`，监听数据库变动，注册系统闹钟。

---

### 阶段六：高级特性 (Advanced / Polish)

**目标**：锦上添花的功能。

1. **自动识别 (Shadow Tracking)**
    * 集成传感器插件（Pedometer, Geolocation）。
    * 实现本地 `ShadowEvents` 表的写入和过期清理。
    * UI：实现“影子转正”的确认卡片。

2. **Tag 系统**
    * 如果 MVP 后期决定加入 Tag，在此阶段引入 `TaskTagRelations` 表。

3. **性能优化**
    * 分析 SQL 执行计划，优化索引。
    * 各种动画和交互细节打磨。

---

### 总结：开发优先级排序

1. **P0 (生死攸关)**:
    * TimeProvider (时间校准)
    * SyncService (基础同步协议)
    * Task/Activity 表结构与 DAO
2. **P1 (核心价值)**:
    * Recurrence Engine (复发计算)
    * Log 写入与状态联动
    * Arena 排序算法
3. **P2 (完整体验)**:
    * 统计图表
    * 本地通知
    * 双轨时间轴视图
4. **P3 (黑科技)**:
    * 自动识别
    * 小组件

建议先用 **1-2 周** 集中攻克 **阶段一和阶段二**。只要数据层和同步层稳了，后面的 UI 开发就会非常快。
